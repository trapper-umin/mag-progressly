## 2. Интерфейс взаимодействия и анализ предполагаемой нагрузки

Для обеспечения гибкости и стабильности системы архитектура взаимодействия строится на принципах REST API и событийно-ориентированной обработки (Event-driven) для тяжелых задач.

### 2.1 Протоколы и структура данных
*   **Основной протокол:** HTTP (TLS 1.2+).
*   **Формат обмена:** JSON. Выбор обусловлен необходимостью поддержки гибких схем данных (JSONB в PostgreSQL) для реализации кастомных полей трекера.
*   **Спецификация:** использование стандарта OpenAPI 3.0.
*   **Стандартизация:** все временные метки передаются в формате ISO-8601 с указанием UTs. Это критично для корректного расчета «серий» (streaks) пользователей в разных часовых поясах.

### 2.2 Модели взаимодействия (Sync vs Async)
Система использует гибридную модель для соблюдения лимитов времени отклика:

1.  **Синхронный обмен (Request-Response):**
    *   Сценарии: аутентификация, создание и редактирование полей, мгновенный ввод ежедневных значений.
    *   Целевой latency (задержка): < 300 мс для 95-го перцентиля. Эта метрика означает, что у 95% пользователей время отклика будет быстрее 300 мс.

2.  **Асинхронный обмен (Task Queue / Webhooks):**
    *   Сценарии: генерация AI-сводок (Ollama), отправка уведомлений (Telegram), подтверждение платежей (YooKassa).
    *   Механика: клиент получает статус "202 Accepted", а сама задача уходит в очередь (Redis). Результат доставляется пользователю позже. Это предотвращает зависание интерфейса при длительных операциях (например, когда нейросеть обрабатывает данные 10–15 секунд).

### 2.3 Оценка нагрузки и пропускная способность
Исходя из бизнес-цели BZ1 и расчетной емкости в 10 000 активных пользователей в день (DAU), определены следующие параметры:

*   **Интенсивность запросов:**
    *   Среднесуточная: около 150 000 – 200 000 запросов.
    *   Пиковая (Peak Load): ожидается в утренние (08:00–10:00) и вечерние (20:00–23:00) часы. Проектируемая нагрузка в пике — 80–120 запросов в секунду (RPS).
*   **Объемы данных (Payload Volumes):**
    *   Обычный запрос: около 2–4 кб на один пакет данных.
    *   AI-контекст: при передаче истории за неделю в Ollama — до 20–50 кб на запрос.
*   **Пропускная способность:** требуемая полоса пропускания — 10–15 мбит/с, что полностью покрывается ресурсами современных облачных провайдеров.
*   **Распределение во времени:** 
    *   80% нагрузки: операции чтения и записи ежедневных данных (CRUD).
    *   5% нагрузки: тяжелые аналитические запросы к ИИ, распределенные во времени с помощью очереди задач.

### 2.4 Ограничения пропускной способности (Rate Limiting)
Для защиты от DoS-атак и перегрузки ИИ-движка (Ollama) вводятся лимиты:
*   Для Free-пользователей: 30 запросов в минуту.
*   Для Pro-пользователей: 100 запросов в минуту.
