## 1. Сколько баз данных и почему

Мы используем **два хранилища данных с разным назначением**:

| Хранилище | Тип | Данные | Время жизни данных |
|---|---|---|---|
| **PostgreSQL** (основная БД) | SQL, реляционное | Все доменные данные: пользователи, трекеры, записи, цели, подписки, платежи, AI-сводки, уведомления | Постоянное |
| **Redis** | NoSQL, key-value in-memory | Сессионные токены magic link (TTL 15 мин), rate limiting, очередь фоновых задач (AI, уведомления, автосписания), краткоживущий кэш | Секунды - часы, есть естественный TTL |


Почему не одна БД:

- **Очередь задач и rate-limiter в PostgreSQL** - это постоянные
  `INSERT/DELETE` по горячей таблице, конкуренция за блокировки и вакуум:
  деградация именно тех операций, для которых требование - p95 < 300 мс
  (итерация 4, раздел 2.3). Redis делает это за O(1) в памяти.
- **Доменные данные в Redis** — потеряли бы транзакции, ссылочную целостность
  и durability: платёж нельзя хранить в хранилище, которое может быть
  очищено по LRU.

Почему не три и больше (например, отдельный документный стор для AI-сводок
или колоночная СУБД для аналитики): при целевой нагрузке 10 000 DAU и
150-200 тыс. запросов в сутки дополнительные СУБД дадут только операционную
сложность (резервное копирование, мониторинг, согласованность). Полу-
структурированные данные (ответы LLM, ограничения полей) покрывает JSON
внутри PostgreSQL, а аналитические запросы - индексы и представления.

Итог: **одна реляционная БД как единственный источник истины + одно
in-memory хранилище для эфемерного состояния**. Результат итерации основной БД; Redis описан в архитектуре итерации 4 и схемы
данных не требует.

## 2. SQL или NoSQL: обоснование выбора

Для основной БД выбрана **реляционная СУБД PostgreSQL 16**. 

Мы выбрали PostgreSQL, потому что наши данные сильно связаны и важно,
чтобы база сама не давала сохранить неправильные связи; кроме того,
нужно сохранять несколько записей одной операцией целиком,
часто соединять таблицы и считать итоги,
а структура данных у нас понятная и стабильная, плюс по 152-ФЗ нужно,
чтобы пользователь физически не мог увидеть чужие строки - всё это PostgreSQL даёт из коробки,
тогда как в чистом NoSQL пришлось бы проверять связи в коде, бороться с огромными документами, 
сложными объединениями и транзакциями, а защиты на уровне строк нет; 
при этом гибкие куски данных, которые только читают целиком, 
мы храним в PostgreSQL в виде JSON, так что получаем удобство NoSQL без второй базы.

**Где мы сознательно используем NoSQL-подход внутри PostgreSQL.**
Не всё в схеме строго нормализовано, и это осознанное решение:

- `tracker_fields.constraints JSONB` — ограничения поля разнотипны
  (`min/max` для шкалы, `options` для выбора, `unit` для числа). Выносить
  их в реляционные таблицы - 4 лишние таблицы без единого выигрыша: по
  ним не ищут и не соединяют, их только читают целиком.
- `ai_summaries.insights / advice JSONB` - список строк переменной длины,
  возвращаемый LLM. Хранится и отдаётся как массив; разбор показан в Q9.
- `field_values.value TEXT` для всех шести типов — компромисс EAV-lite:
  валидация типа выполняется приложением (операция
  `ПолеТрекера.проверитьЗначение`), а для аналитики значение приводится к
  `numeric` на лету (Q5). Альтернатива - 6 таблиц значений по типам -
  усложнила бы каждый запрос ради строгости, которую всё равно
  контролирует конструктор полей.

То есть мы взяли реляционное ядро там, где нужны целостность и агрегации,
и документные островки там, где данные атомарны для чтения. Гибрид даёт
оба качества без второй СУБД.

**Почему не NoSQL (MongoDB и т.п.):** трекер с embedded-записями
в одном документе упрется в лимит размера документа за годы ежедневных
записей; ссылки user→subscription→payment всё равно потребуют joins
($lookup); транзакции по нескольким коллекциям сложнее и медленнее;
RLS-эквивалента нет.

## 3. От диаграммы классов к схеме БД

Схема спроектирована **напрямую из проектной диаграммы классов итерации 3**
по правилам объектно-реляционного отображения:

| Класс (диаграмма) | Таблица | Правило отображения |
|---|---|---|
| `Пользователь` | `users` | Класс → таблица; атрибут `идПользователя: UUID` → PK |
| `Сессия` | `sessions` | Класс → таблица; связь владелец 1—0..* → FK + индекс |
| `Подписка` | `subscriptions` | Кратность подписчик 1—0..1 → `UNIQUE(user_id)` |
| `Платёж` | `payments` | Статус `= СОЗДАН` → `DEFAULT 'CREATED'` |
| `Трекер` | `trackers` | Атрибут `активен = истина` → `DEFAULT TRUE` |
| `ПолеТрекера` | `tracker_fields` | Композиция трекер 1—1..* поля → FK `ON DELETE CASCADE` |
| `Запись` | `entries` | Заполнение за конкретную дату → `UNIQUE(tracker_id, entry_date)` |
| `ЗначениеПоля` | `field_values` | Композиция с двух сторон → составной PK `(entry_id, field_id)` |
| `Стрик` | `streaks` | Кратность трекер 1—0..1 → PK по `tracker_id` |
| `Цель` | `goals` | Три ассоциации (автор, поле цели, группа) → три FK |
| `ГруппаЦелей` | `goal_groups` | Класс → таблица |
| `AI-сводка` | `ai_summaries` | `Список<Строка>` инсайтов/советов → JSONB |
| `Уведомление` (глоссарий) | `notifications` | Класс → таблица |
| `Тариф` + лимиты (FR-17) | `tariff_limits` | Перечисление + справочник лимитов модуля admin |
| Прогресс, Аналитика (представления в глоссарии) | `v_tracker_fill_30d`, `v_goal_progress` | Классы-представления → SQL VIEW |
| Перечисления `ТипПоля`, `Периодичность`, `СтатусЗаполнения`, `Тариф`, `СтатусПлатежа`, `СтатусЦели` | `CREATE TYPE … AS ENUM` | enumeration → ENUM-тип |

Граничные (`Страница*`, `Клиент*`) и управляющие (`Менеджер*`, `Сборщик*`)
классы в схему не попали - это классы поведения, а не данных; для них
хранилище не требуется.

## 4. Структура базы данных

14 таблиц в четырёх группах. ER-диаграмма:

/Вставить картинку/

| Группа | Таблицы |
|---|---|
| Доступ | `users`, `sessions` |
| Монетизация | `tariff_limits`, `subscriptions`, `payments` |
| Ядро трекинга | `trackers`, `tracker_fields`, `entries`, `field_values`, `streaks` |
| Цели и AI | `goal_groups`, `goals`, `ai_summaries`, `notifications` |

Ключевые ограничения целостности (полный DDL — `db/schema.sql`):

- `entries`: `UNIQUE (tracker_id, entry_date)` — одна запись трекера на дату;
- `field_values`: составной PK `(entry_id, field_id)` + триггер
  `check_value_same_tracker()` - поле и запись обязаны принадлежать
  одному трекеру;
- `streaks`: `CHECK (record_len >= current_len)`;
- `subscriptions`: `UNIQUE (user_id)` (0..1 по диаграмме), история
  подписок восстанавливается из `payments`;
- `payments.external_id UNIQUE` — идемпотентность webhook'ов YooKassa;
- все композиции — `ON DELETE CASCADE`, удаление аккаунта (FR-04)
  выполняется одним `DELETE` на `users` (либо мягкое — `deleted_at`);
- индексы под горячие запросы: `(tracker_id, entry_date DESC)`,
  `field_values(field_id)`, `sessions(token)`, `ai_summaries(user_id,
  period_start DESC)`;
- RLS-политики на `trackers`, `entries`, `field_values` — изоляция данных
  пользователей на уровне СУБД (152-ФЗ).

Схема находится в **3НФ**: неключевые атрибуты зависят только от ключа,
транзитивных зависимостей нет (тариф подписки - это FK на справочник, а не
набор колонок). Сознательные отступления от канонических форм - JSONB.

## 5. Проектные решения в схеме

1. **UUID-первичные ключи** (`gen_random_uuid()`): идентификаторы можно
   генерировать на клиенте/в worker'е без обращения к БД; они не раскрывают
   количество пользователей и удобны в webhook-метаданных YooKassa.
2. **Статус записи хранится** (`entries.status`), а не вычисляется каждый
   раз: он нужен календарю за один запрос без соединения со всеми
   обязательными полями. Пересчёт — при сохранении записи (UC-01).
3. **Стрик — материализованная таблица** `streaks`: читается за O(1) на
   каждом открытии трекера, а пересчитывается фоновым worker'ом после
   записи (проверка Q4 показывает совпадение хранимого и пересчитанного).
4. **Представления как read models** (`v_tracker_fill_30d`,
   `v_goal_progress`): «Прогресс» и «Аналитика» в глоссарии — именно
   представления; SQL VIEW фиксирует этот контракт на уровне БД.
5. **Справочник лимитов `tariff_limits`** вместо констант в коде: модуль
   admin меняет лимиты тарифов без релиза (FR-17, итерация 4).
6. **Относительные тестовые данные** (`CURRENT_DATE - n`): датасет не
   «протухает» — календарь, стрики и лимиты осмысленны в любой день
   запуска.

## 6. Проверка работоспособности

База развёрнута на PostgreSQL 16, наполнена согласованным датасетом
(`db/seed.sql`): 5 пользователей на трёх тарифах, 6 трекеров со всеми
шестью типами полей, 106 записей за 60 дней с честными пропусками, 386
значений, 6 целей, 7 платежей во всех статусах, 3 AI-сводки.

Прогон `db/queries.sql` — **16 проверок, все успешны**
